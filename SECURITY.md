# Security policy

Report suspected vulnerabilities privately through [1904's contact form](https://1904.ai/contact). Identify the product as **1904 Desktop** and mention if the issue also affects the hosted dashboard. Keep vulnerability details out of public issues, pull requests, and comments.

Include the affected version and operating system, steps to reproduce the issue, and the impact you observed. Redact account details, session cookies, tokens, and private task content. If the report needs sensitive material, request a secure way to share it.

Please coordinate public disclosure with the maintainers so they can investigate and address the issue.

## What the app can do on your computer

1904 Desktop shows the hosted dashboard in a sandboxed window. With **Use My Computer**, it can also run shell commands on your computer for a task’s agent. That feature is off until you choose **1904 → Use My Computer…** and confirm. Every rule below is enforced on your computer, so it holds even if the cloud side is compromised. Once connected:

- **Origin.** 1904 Desktop answers a request only for a message its own window sent within the last six hours (it stamps each one with a proof made from a per-computer key the page never sees), or inside away mode you started on this computer for that task. Anything else is refused without a prompt.
- **What the stamp guarantees.** The dashboard page is served by 1904, so a script on it can send a message too. 1904 Desktop therefore stamps a message only when you pressed a key or clicked in its window within the previous 10 seconds and the window is in front; the app sees that input itself, and events a page makes up do not count. Anything else leaves unstamped and is noted in this computer’s log. So a message counts as sent from this computer only while you are actively using 1904 Desktop’s window. It does not prove you wrote that message: a compromised page could send its own in those seconds. Every command it leads to still needs your approval on this computer and runs in the sandbox.
- **Approval.** Every command waits for your approval in 1904 Desktop’s own prompt window (a local page with no script of its own, loading nothing from 1904) that shows all of it, unless an allowance you chose there covers it, or it came from a message sent elsewhere inside away mode. Nothing a web page or 1904 sends can approve it for you, and settings on 1904, including a task’s Auto or Bypass mode, never do. A command too long to show in full is never run. The prompt opens after a pause in your typing and clicking, Decline has the focus, and Run takes no answer until the window has been in front for a moment and the whole command has been in view; the main process enforces the same delay. The window answers with a one-time value for the request it shows, and only from its own page.
- **Allowances.** "The rest of this message" ends when this window sends the task another message, or after 30 minutes. "Everything this task asks, for" lasts 30 minutes to 8 hours and covers only messages this window sent to that task, for the same app and folder. Both live in memory only and end with Pause, Disconnect or quitting. On macOS they never cover full access; on Windows, which has no sandbox, they cover every command. An approved command starts only after 1904 confirms the request still stands.
- **Sandbox (macOS).** By default a command runs under `sandbox-exec` with a profile that denies everything and then allows only: running and forking programs, signals to its own processes, named system facts, semaphores and shared memory, a short named list of system services, reading the system (not any home folder, `/Users/Shared`, other drives, Homebrew’s and MacPorts’ `var` folders where local databases keep their data, or other apps’ temporary files), reading the app’s folder, its own temporary folder and named toolchain folders, and writing the app’s folder and its temporary folder. In the app’s folder it can write inside the app’s own `.git` folder only what ordinary git work writes there (objects, refs, reflogs, the index, `HEAD` and the state of a merge, rebase, cherry-pick or revert), never git’s settings, hooks, `info`, worktree links or other object stores, and it cannot create a `.git` file or folder anywhere else. It also cannot write editor, dev container and coding-agent settings (`.vscode`, `.idea`, `.zed`, `.cursor`, `.devcontainer`, `.claude`, `.mcp.json` and similar), commit-hook configurations (`.husky`, `.githooks`, pre-commit, lefthook, lint-staged), `.envrc` or mise settings. These rules match in any letter case, since macOS disks usually ignore case. Credential stores, git’s global settings (`~/.gitconfig`, `~/.config/git/config`, which can hold tokens), global npmrc files, Keychains and 1904 Desktop’s own data come last and win over every allowance, for reading and writing; git inside the sandbox gets a settings file with only your name and email. The command’s temporary folder is deleted afterwards inside a sandbox of its own that can write only that folder. It cannot send Apple events, open apps, files or links, start background jobs, write preferences, mount disks, or use the pasteboard or the window server. No path is ever written into the profile text; each is passed to `sandbox-exec` as a parameter, so a folder name cannot add a rule. The app’s folder can never be, contain, or sit inside a credential store, 1904 Desktop’s data, `~/Library` or a hidden folder in the home folder; saved folder choices are checked again every time they are read.
- **Network.** A sandboxed command has no network unless you allow it in the prompt. With it, it can reach the internet but not loopback services on this computer, and can listen on loopback only; a service listening on all of this computer’s addresses may still be reachable through its network address. Network off is not a privacy control: a command’s output returns to 1904, so whatever it can read can reach 1904 that way.
- **Limits of the sandbox.** The sandbox protects your computer while the command runs. It does not make what the command leaves in the app’s folder safe to run: scripts, `package.json` scripts, tests, installed dependencies (`node_modules`, `.venv`), symbolic links and git history it writes there run or are followed with your full permissions when you, your editor or your tools use them later outside the sandbox, and some editors load project code as soon as the folder opens. The protected files above close the most direct of these paths, not all of them. Known gaps: a folder in the app’s folder can be made to look like a bare git repository, which git trusts when run inside that folder (git’s `safe.bareRepository=explicit` setting stops that); and a merge, rebase, cherry-pick or revert the command leaves in progress is the command’s work, so check it before you continue it outside the sandbox. A process a command deliberately detaches (with `setsid` or a double fork) can outlive the command; it stays inside the sandbox.
- **Full access.** A command that asks for full access runs as the user signed in to this computer, with that user’s permissions, files, keys and network. On macOS it is asked about every time, confirmed with Touch ID where the Mac has it, and never covered by an allowance or away mode.
- **Windows.** 1904 Desktop has no sandbox on Windows yet, so every Windows command is treated as full access, your allowances cover it, and away mode is not offered. A background process a Windows command starts can keep running after the command exits, because `taskkill /T` cannot follow a parent that has already exited. On macOS, background processes a command starts end with it.
- **Environment.** A command never inherits 1904 Desktop’s environment: it gets `PATH`, `HOME`, `USER`, `LOGNAME`, `SHELL`, `LANG`/`LC_*`, `TERM` and its own temporary folder (on Windows, the system variables Windows needs), plus, when sandboxed, `GIT_CONFIG_GLOBAL` for a git settings file with only your name and email, and shells start without startup files.
- **Away mode** is started only on this computer, for one task, for at most 8 hours and a command budget, after native questions and then Touch ID naming 1904’s own title for the task it started; without Touch ID, a last question names that title and the limits, and Cancel ends it at once. Started from the dashboard page, it also needs your recent key press or click in the window. It covers sandboxed commands from messages sent elsewhere only; a message from this window always asks. 1904 can end it but never start or extend it.
- **Keys.** The token and proof key 1904 issues for this computer are kept in the app’s data folder, encrypted with the system key store (Keychain on macOS, DPAPI on Windows) through Electron `safeStorage`. Without that storage, the computer is not connected. Only the app’s main process reads them.
- **Connecting.** The connect prompt names the 1904 account the computer is joining; Cancel takes the connection back from 1904 at once.
- **The page.** Only the agents dashboard and Computers in 1904 Settings can reach Use My Computer, and only the agents dashboard’s messages are stamped. They can only ask whether this computer is connected or paused, open the connect prompt, and open the away-mode questions (the last two only right after your key press or click). They cannot run or approve a command, read output, or read either key. Token-bearing requests to 1904 never follow redirects.
- **Controls.** **Pause Use My Computer** in the 1904 menu stops all requests. 1904 Desktop keeps its own log of every command, decision and the end of its output on this computer. **Disconnect This Computer…** asks 1904 to revoke the token and deletes the keys from this computer, even when 1904 can’t be reached; disconnecting in 1904 Settings also revokes it.

The [README](README.md#use-my-computer) describes the feature in full. Reports of a way to run a command without the person’s approval or outside the sandbox, to approve one from a web page or from 1904, to make a request pass the origin check, or to read the token or proof key are in scope and especially welcome.
